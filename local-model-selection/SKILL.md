# 本地受限硬件的模型选型与核验

## When to Use

- 用户问「我这台机器上该跑哪个开源模型」，或要在他机器上排候选。
- 需求带**去审查（uncensored）**；或用途涉及危险代码审查、角色扮演这类需要无拒绝输出的场景。
- 要判断「某模型坏了 / 某张量异常 / 某版本就是上一代」这类传言真假。
- 要在受限显存下做 KV 与专家卸载的内存规划。
- 要把选定模型**实际跑起来**：推导 `--n-cpu-moe`、判断加载模式、从启动日志核账与排障 PP/TG。
- **核验已部署模型的服务配置**：启动脚本里的采样 / 上下文 / 输出参数是否符合**官方卡**的推荐档（卡按任务分档，agentic 有专属档）——见 `references/serving-params-vs-card.md`。

## 铁律

1. **先算内存账，再谈模型强弱。** 顺序：显存容量 → KV（若必须进显存）→ 权重总量 → 激活量（决定速度）。没算账就推荐模型 = 浪费用户时间。
2. **只能部分卸载的机器必须选 MoE。** 稠密模型的层卸载，每个 token 都要把卸载的那部分权重整个读一遍；MoE 只读激活的那几个专家——差一个数量级。用户给出「必须部分卸载」约束时，所有稠密候选直接出局，哪怕分数更高。
3. **KV 从 config.json 自己算，别抄第三方站。** 第三方「这个模型要 X GB」常按稠密公式估，对混合注意力 / MLA 架构能错十几倍。
4. **同一把尺子才可比。** 跨基准、跨口径的数字不可比；**同一个基准名也可能是不同协议**（生成式 vs 对数似然），指纹与可比判据见 `references/benchmark-sourcing.md` §七。优先找「同一张表列了两个模型」的源再开比（§八）。去审查类目用 UGI 榜的四轴。
5. **权重层面的断言自己读权重验，不转述讨论区。** 方法见 `references/hf-weight-forensics.md`，脚本 `scripts/hf_tensor_stats.py`。
6. **交付按用途给落点**，别把十几个候选平铺让用户自己挑；同时显式列出「装不下」的排除项及原因。用户问「该跑哪个」时，**第一句就给结论 + 要下的那一个文件**，支撑分析放后面或等追问。把分析堆在前面再给建议，会被顶回「别搞太复杂，直接告诉我」。
7. **候选名单必须带同尺表。** 只报模型名或散落各处的数字会被顶回「没有我要的量化对比」。凡「Top N 候选」，每一个都要落进同一张表（同列指标、同来源等级）。
8. **名单在两轮之间收窄时，摘掉的候选必须当场给理由。** 静默消失 = 漏报，用户会发现并质问（「X 怎么丢了？」）。
9. **「某站/某榜覆盖了模型 X」这类断言，打源站证明，不许凭记忆。** 见 `references/benchmark-sourcing.md`。
10. **禁止跨变体搬基准数字。** 同族同名的稠密版与 MoE 版是不同模型，一个的数字不能给另一个背书。引用前逐字核「模型全名 + 参数构成」与讨论对象一致，不一致就明写「这是 X 的数据」。
11. **卸载参数从真实张量拆分推导，不估。** 跑 `scripts/gguf_expert_split.py` 拿专家/非专家体积，再按「可用显存 − 非专家 − KV − 缓冲」反推能留 GPU 的专家块数，两者之差就是卸载块数（**注意 N 数的是前 N 层**，自证方法与方向细节见 `references/moe-offload-deployment.md` §1——方向搞反不改内存账，但会让你读错日志与摆放）。见 `references/moe-offload-deployment.md`。**但动手前先逐字读母版脚本**：若它走 `--fit on --fit-target <MiB>`（引擎自动分配），手算 `--n-cpu-moe` 全是白工——那个变量很可能只用于 `echo` 打印、命令行根本没引用。
12. **启动脚本的采样 / 上下文 / 输出参数必须逐项对官方卡，不是随便填的。** 卡按**任务档**给不同值（思考·通用 / 思考·精确编码 / 非思考各不同），**agentic 有专属档**，且 benchmark 脚注里写的才是该任务类型的真实评测配置。三个常被漏的轴：**上下文长度**（卡常明写「至少多少才保得住某项能力」，受限显存上常被下调——是取舍，但要知差距）、**输出长度**（agentic 有专属预算，而服务端不设 `max_tokens` 时天花板 = `ctx − prompt`，**「不设上限」只在窗口够大时才等于「给足」**）、**思考开关方式**（有的由提示词里的控制 token 决定，不在采样参数里）。核验程序与四家实测卡值见 `references/serving-params-vs-card.md`。

## 步骤

1. **定约束**：显存 / 内存 / 系统 / 是否必须 KV 进显存 / 是否只接受 MoE / 推理栈 / 语言权重 / 用途（编码、安全、RP、通用）。先查账本，缺的再问。
2. **收集候选**：HF 趋势与下载榜 + 开源模型发布时间线站；直接查 lab 的 HF org 按创建时间排，别只信新闻稿。**把小厂一起扫**，但一律按第 1 步约束过筛。
3. **算 KV 与内存账**，按架构分类（公式与实例见 `references/kv-cache-estimation.md`）。
4. **同尺对比**：去审查类目拉 UGI 原始 CSV（源见 `references/uncensored-triage.md`），取 UGI / W-10 / NatInt / Writing。写作/RP 看 Writing，安全与知识看 UGI + NatInt。
5. **核验可疑断言**：任何「某模型坏了 / 某张量异常 / 某版本就是上一代」都自己测（`references/hf-weight-forensics.md`）。
6. **交付**：对照表 + 按用途排序 + 排除项 + 下一步的最小验证动作。
7. **部署**：推导卸载层数 → 判断加载模式（mmap vs `--load-mode none`）→ 从启动日志核账 → 用边际速率分开「首块停顿」与「稳态慢」。全流程见 `references/moe-offload-deployment.md`。

## 坑（每条都在本类任务里踩过）

- **把稠密层卸载当成 MoE 专家卸载。** 用户会当场纠正。见铁律 2。推荐前自问「这个候选是稠密还是 MoE」。
- **抄第三方的 KV 或体积数字。** 有人按稠密公式估 MoE / 混合模型的 KV，误差达一个数量级。自己从 config 算。
- **config 里同时出现 `num_key_value_heads` 与 `kv_lora_rank` 时按 MHA 算 KV。** 有 `kv_lora_rank` 就是 MLA，缓存的是压缩潜变量，KV 小得多。
- **把「全族都有」直接读成「所以是特征不是缺陷」。** 同一份数据同样支持「全族共有的缺陷」——两种读法并列，并说明什么证据能区分它们。只报一种 = 过度断言。
- **拿原始 GSM8K 比思考模型。** 思考预算耗尽的空回答记 0 分；原始差距可达 40 分，剔除空回答后常 <3 分。必须先修正再比。
- **在 acc 类指标和 perplexity 之间求平均。** 单位不同，不能混进同一个平均。
- **以为去审查无损、或凭下载量排序。** 都不是。见 `references/uncensored-triage.md`。
- **跨版本比较只看一个张量就下「这是两代新模型」。** 逐类抽样（norm、bias、投影）才有信息量。
- **用同族另一个变体的基准数去推当前变体。** 稠密 27B 的取证/基准数字不能搬给同名的 35B-A3B MoE。引用前逐字核模型全名与参数构成。见铁律 10。
- **把厂商模型卡的名次当结论。** 厂商自选考纲与第三方聚合（把对手的全部公开行也算进去）会给出**相反**名次，两边都可能为真；标来源等级，并说明差异来自「共享行」还是「覆盖广度」。
- **长周期 agentic 只挑峰值分。** 超时率、P95 延迟、输出 token 膨胀、逐次可重复性才决定长跑能不能用——峰值高但有这些毛病的模型会在循环里拖死任务。
- **拿错评测轴。** HLE 与日常/agentic 编码**弱相关**（评测方自己声明），且「带工具」与「闭卷」是两个口径；agentic 工作负载看 Terminal-Bench / SWE-bench Pro / τ²-bench / Toolathlon / MCP-Atlas。
- **断言某榜覆盖了某模型却不去核。** sitemap.xml 枚举真实页面，候选 URL 做 404 探测；凭印象说「它有覆盖」= 瞎说。方法见 `references/benchmark-sourcing.md`。
- **给 MoE 抄稠密模型的启动脚本当母版。** 稠密母版没有 `--n-cpu-moe` / `--load-mode none` / `--ubatch-size`，抄完 MoE 跑不动或首块奇慢。按架构挑母版，并把每个 flag 过一遍「这个模型需不需要」。
- **无条件把 mmap 换成 `--load-mode none`。** 它要求 CPU 侧专家**一次性常驻内存**；装不下时 mmap 正是让它能跑起来的东西。先比「CPU 侧专家总量」与「启动时空闲内存」。
- **拿累计平均判断 PP 快慢。** 日志里的 prompt-processing 速率是累计值，首块停顿会被摊薄；逐行相减算边际，才能分清是加载/分页问题还是算力问题。
- **按「家族」标签聚合基准列，把不同变体揉成一行。** 一个家族名下常混着多个尺寸/变体（31B 与 26B-A4B 同属 gemma-4），对它取中位数或均值 = **静默把 31B 的数报成 26B-A4B 的**，且数值看着完全合理、不报错。**聚合键必须是「共享该指标的确切模型身份」，不是家族名。** 出表后抽 2–3 行回原始卡逐项核；见铁律 10。
- **对着 `--fit` 自动分配的脚本手算 `--n-cpu-moe`。** 用户脚本里常有 `set N_CPU_MOE=N` 却不被命令行引用（只给 `echo` 看），真正分配交给 `--fit on --fit-target <MiB>`。**改脚本前逐字看命令行本体**，只改 `MODEL_PATH` / `--alias` / 端口这类必要项，不顺手动分配逻辑。回报实测性能时，权重落到 GPU/内存的拆分要用 `nvidia-smi` 占用 + 进程工作集反推（引擎自己的分配明细只在控制台窗口里，远程读不到），并明说是反推值。
- **只看模型卡就下性能结论。** 同架构、同底座、只换量化格式的两个文件，实测差距可以到数倍（本机实测：同一 Qwen3.6-35B-A3B，Experts-Only 高精度非专家的 23.06 GiB 版 → PP ~300/TG ~17 t/s；全量低比特的 15.85 GiB 版 → PP 1031/TG ~79 t/s）。**非专家部分的精度保留策略直接决定能上多少权重到卡**，这是选量化档时比参数名更重要的轴。 同族里有的带 MTP 之类草稿头、有的一个都没有——带的一方白拿数倍 TG，不带的一方怎么调参都追不上。**这是下载前就能查的家族级事实**（扫仓名 + 文件清单），必须进对比表；只比参数量与分数会得出错误的部署结论。
- **换量化档只验速度不验质量。** `timings` 只告诉你快了没快；混合精度量化「快且没坏」是待验假设，不是结论。换档后跑一遍判分题库做回归，方法（协议四条：不传 temperature/top_k、reasoning 必开、不设 max_tokens、逐字节同题；INVALID 闸；答案 key 自校；天花板效应；直连 curl 形状）见 `references/quant-quality-probe.md`。
- **自己设的每个上限都要装闸，否则判分器的残缺会伪装成模型的失败。** 输入侧（贴给模型的源文件被 `MAX_SRC_CHARS` 截断）与输出侧（`max_tokens` 不够）是同一个病：不报错、不异常，只交出一个看着正常的假数字，而且系统性把分数压低（实测：同一个模型 AIME 从 20% 变 100%，差的只是把上限提到题能跑完）。输出侧读 `finish_reason`，`length` 即 INVALID、不进分母；输入侧拼接时留 `(truncated)` 标记并在运行时拒绝。**指标中位数恰好等于自设常量**（如提示词长度中位数 == cap）就是上限正在生效的红灯。提一档不等于够：只要 INVALID 不为零就继续提。
- **拿自建选择题库当质量对照，用户不认。** 他会点名要「原题」（SWE-bench / Terminal-Bench 这类）——自建题库降级为快速冒烟。真实基准上还有两件必做的事：**判分环境必须先拿 gold patch 探路**（test_patch 应用后必须失败、gold 应用后必须全绿），不探路测出来的分数全是废数；**patch 应用要多级容错**，`git apply` 对 hunk 计数差 ±1 直接 `corrupt patch` 拒收而 GNU `patch -p1` 照收——只挂 `git apply` 会把模型做对的判成 0。**拿到通过率先别报**：补丁没应用上的题不是模型的失败，要分别报有效分母、小样本先做显著性检验、并**把每题 diff 与 gold 并排读**（聚合分给出「不显著」时，读 diff 得到的模式常是一致的、可解释的）。**规格对齐优先于提速**：为省时间把提示词裁到「只给该改的那段」会删掉要测的技能（模型要当自主 subagent 用时尤其如此），要压时间预算就砍题数不砍保真度。**还有两条比提速重要**：判分层必须**逐条解析测试状态并带上 PASS_TO_PASS 回归闸**——自己拍脑袋写容易得出「所有模型一律 0 分」的假结果，而且不报错；**优化前先冷热各跑一次**，首轮慢常是系统对新文件的实时扫描，不是你的代码慢。流程与纪律见 `references/code-patch-probe.md`。
- **把 A 模型的 agentic 采样值填进 B 模型的脚本。** 各家的「编码/agent」档数值看着都合理（Xing4.0 是 0.8、Qwen 是 1.0、Gemma 是 1.0 且 top_k=64），单看脚本发现不了。**逐项对当前卡的推荐表 + 评测脚注**，不靠印象里的值——卡也会改（同一张卡曾同时挂着两段互相矛盾的推荐，被讨论区点出后才统一）。另：量化仓的卡通常**没有任何采样建议**，要去上游 lab 的原始卡。见 `references/serving-params-vs-card.md`。
- **用文本搜索判定某个 flag 存不存在。** 脚本注释里常写着「本族无 MTP 权重，故不写 `--spec-type`」——搜索会命中注释里的那串字，报出「flag 还在」。**判定命令行参数一律读命令行本体**，或把搜索范围限定到调起服务的那段。
