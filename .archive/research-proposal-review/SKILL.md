# 科研提案审查与整改

**用途**：在投入资源前严格审查科研/学术提案（或方法论设计）：发现漏洞与不可行之处、诚实评估价值与可行性、产出带阶段门（Go/No-Go）的整改计划与逐节修改意见，并在修订后做一致性核对与残留扫描。

## 何时使用
- 用户要求对科研提案、论文计划、学位论文设计、方法论框架「找漏洞 / 评估价值与可行性 / 给整改策略和修改意见」。
- 多智能体评审闭环在场（魔鬼代言人 v1/v2 → 元评估者校准 → 用户裁决 → 并入 plan）。

## 核心流程

### 1. 按声明类型分解提案（禁止把提案当一整块评审）

| 声明类型 | 验证方法 |
|----------|----------|
| 文献空白 | 联网检索；**必须查邻近领域**，不只查精确短语（"零先例"几乎总是过度声明，诚实的空白通常是**特定组合**） |
| 工具链可行性 | 核查包是否存在于**声明的语言**生态；心算冒烟测试附录代码（import 真的存在吗？） |
| 数据构造 | 核对事件语义、数据集规模/成本、污染源（bot/爬虫）、删失/选择偏差 |
| 统计有效性 | 分布陷阱（零膨胀）、功效不足、参数等价断言、结构断点 |
| 时间线 | 对照单作者+并行产品工作量做现实校验；通常低估 50–100% |
| 预期结果 | 点估计改区间；设"最小可发表标准" |

### 2. 工具链核查（最常见的 P0）
附录代码 import 不存在的包 = 作者从未跑通过管线，这是 P0 而非小瑕疵。例：`fracdiff` 是 R 包（Python 无）、`statsmodels` 无 ARFIMA（d 仅整数）。整改：要求 Phase 0 设**工具链冒烟测试**关卡（已知参数的模拟数据恢复测试）。若生态空白，自实现+开源反而可转为工具贡献。

### 3. 数据构造核查
- **事件语义**：如 GitHub `PushEvent` 计数是 push 次数 ≠ commit 数（真值在 `payload.size`）；`PullRequestEvent` 含全部动作需过滤 `action='opened'`。
- **污染**：bot 账号（dependabot/renovate/github-actions）需双层过滤（名称模式 + 已知 bot 名单）。
- **成本诚实**：GH Archive ≈17TB；BigQuery 1TB/月免费额度 1–2 次全扫描即耗尽 → 缩范围或抽样，写明成本上限。

### 4. 统计陷阱扫描（最高价值步骤）
- **零膨胀→伪长记忆**：>90% 为零的计数序列经 GPH 会产生 d>0 伪迹（Saha 2020 "Pitfalls in long memory research"；Granger & Hyung 2004）。整改：零模型对照仿真（两阶段零膨胀模型 + 匹配零占比的对照序列，比较拒绝率）+ size/power/FDR 校准。
- **聚合伪迹**：异质短记忆个体聚合后可产生伪长记忆（Granger 1980）→ **个体层面先行**，群体/子群体仅作探索性。
- **短序列功效不足**：GPH 在 52–104 观测上 SE≈0.15–0.25 → 单个体功效仅 30–45%；武断阈值（如">40% 个体显著"）可能在效应真实存在时统计不可达。整改：**模拟功效曲面反推阈值并预注册**。
- **参数等价断言**（α↔d↔H、连续↔离散）：标为"待仿真验证的假设"而非给定前提；不成立则删除统一叙事、保留离散框架。
- **结构断点**：要求分段平稳 pipeline（Bai-Perron 断点 → 段内估计 → Chow 稳定性检验）。

### 5. 诚实校准可行性评分
明确区分两个数字：**「按当前版本直接执行的失败概率」**（存在确定性缺陷时可 >60%——不可运行代码、错误 SQL、成本错估）与**「整改后的成功概率」**（通常 65–75%）。元评估者会攻击过度悲观；同时给出两个数字 + 修订 delta 逻辑即可化解争议。

### 6. 整改计划结构
- **Phase 0 预验证 + Go/No-Go 决策关**（"四面墙"）：工具能跑 / 阈值可达（功效反推）/ 效应非伪迹 / 规则已预注册锁定。任一墙塌 → 触发预案（放宽资格、粗化聚合、换叙事）或终止。
- **预注册在 Phase 0 开头写、数据检验前冻结**（看到结果后再写 = 失去意义）。Primary 冻结，Exploratory 明确标注、不做多重校正。
- **范围收敛**：框架型组件（Kalman/MPC/TE 类）移至附录或**第二篇论文**——两篇论文 > 一篇大而全。
- **逐节修改意见 R1..Rn**：每个漏洞映射到具体编辑（软化空白声明、修 SQL、替换不可运行代码、补数据质量报告、预期结果区间化）。

### 7. 执行与验证
- 遵守用户归档协议：改前先备份 `……V x.x_Archived`。
- 修订后跑**一致性核对**（每条 plan 要求 → grep 修订稿找落点）+ **残留扫描**（grep 旧版遗留：旧阈值、不可运行 import、旧数据范围、旧时间线、旧"首次/首创"声明、旧期刊目标）。**无输出 = 无残留**为验收标准。

## 多智能体评审闭环（校准模式）
- 魔鬼代言人产 v1（问题发现最大化，常过度悲观）与 v2（务实校准）。
- 元评估者拆分：哪些是真 P0 必须修（零膨胀陷阱、工具链不存在、SQL 语义）vs 哪些过度悲观（可行性评分、砍范围过激）。
- 用户裁决开放问题（Q1..Qn）→ 决策并入 plan delta；**开放问题必须先全部拍板再定稿整改计划**。
- 硬 P0 修复不因范围变化而撤销；只有用户授权项才可改。

## 陷阱
- 把提案当一整块评，不按声明类型分解。
- 不查邻近领域就接受"零先例"。
- 不验证包是否存在于声明语言就信附录代码。
- 对计数数据的长记忆声明漏查零膨胀混淆。
- 阈值不经功效分析就拍脑袋。
- 看到结果后才写预注册。
- 修订文档后忘做残留扫描。
