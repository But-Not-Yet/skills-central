# 成批修复的执行形状（对既有系统）

## When to Use

审查/台账产出待修清单后，对既有系统做集中修复时。主人说「按最激进的方案修」「先立任务面板再开干」时。单体小修不需要本形状，这里是重型批次的定型。与 `engineering-workflow-loop` 互补：那份管八站的全程流程，本技能管「一批修复从起飞到交付」的零件顺序。

## 形状（五步，每步先有实证再推进）

1. **面板与台账先行**。开工先立：①任务面板（聊天内状态板，见 `chat-inline-statusboard`）+ 任务卡（验收标准只写行为、非目标清单、Progress 节）。②待修项逐条落台账（证据/参考/推演/决定）。修复时逐条对账，范围内不即兴扩张。
2. **TDD 循环**。每项：先写会失败的测试。**亲眼见 RED**（测试文件自带 runner：收集 `test_*` 逐条跑、一次列全部失败项，别只跑到第一条断言就停）。再最小实现 → 单套 GREEN → 旧套件全量回归。不攒测试、不先写全实现。测试改 `os.environ` 一律 save/restore（上下文管理器），防串染后续测试。每个行为修复再配**对照测试**（无变化 no-op 契约、开关关闭、既有行为）。修复前后都必须通过，证明没越界。竞态/并发类硬化的 RED 有时不可确定复现。那就退为契约级回归测试（如深拷贝安全、状态独立），并在卡上注明非纯血 TDD。

- **修完补一次反向 RED**：把新代码在**副本**里摸掉（不动真树），确认恰好是新加的那几条测试变红。一条都没红就是测试没咬住实现；红得太多则说明测试耦合到了别的行为。
- **基线本来就红的套件，验收看「失败集差」而不是「红不红」**。先在未改动的父提交上跑同一批文件，两边各取 `pytest <同批文件> -q | grep '^FAILED' | sort` 求差：修复版不许比原版多出任何一条。只看「修后还红不红」会把一堆环境性失败当成护身符——一批 20 条失败里混进 4 条自己新引入的回归，总数上根本看不出来；是差集把它们逼出来的，也才让人回头查到真正的越界路径。
- **任务书的结构性断言先证伪再照做**。「X 是所有路径的唯一入口」「Y 索引可用」这类句子是假设，不是事实。grep 数调用点、`EXPLAIN QUERY PLAN` 读计划，都用实物。更硬的判据是复现：**修完复现还不正常，先怀疑前提而不是加码修**（改了口子才退 2，就证明前提错了）。
- **验收断言要打在用户可见的那条读路径上**。从入口（HTTP handler / CLI 命令）反查到真正排序/渲染的函数，再让脚本断言它。打在另一条同名近似函数上，脚本要么永远不过，要么假过。任务书自带的验收脚本也要先做这一步核对。
- **宿主仓库装在 payload 目录里时，测试授到 home 之外跑**：bootstrap 会读 `<checkout>/../manifest.json`，测试的 home 守卫把这句判成碰生产。用 `git ls-files -z | rsync -a --files-from=- --from0 . /tmp/<copy>/` 导出源码树，`HERMES_HOME=$(mktemp -d)` 起跑；先在未改动的原树上跑一遍确认这不是自己改坏的。
3. **沙箱 E2E 复刻生产**。要模拟生产装载/启动链的验证。先按生产 boot 顺序搭沙箱（见 `hermes-local-ops-troubleshooting` 的「隔离沙箱探针」节，附可复制的起步模板）。并断言「加载的是沙箱对象」防误载真件。拿不到能起动的探针，先别对加载链下结论。
4. **验证四连**。全测试套件 → 官方检查器（validate/lint）→ 自写扫描脚本（版权/特征串等）→ **回滚干跑**（`git revert --no-commit` 后还原，见 `git-repo-hygiene`）。四条全过才算修完。触碰热路径的功能加**数值验收线 + 微基准**。先写线（如 800 KiB 级请求载荷 ≤1 ms）。

  **微基准用 ABBA + 同对象对照组**：每个臂独立临时库，顺序 A/B/B/A 交替抵消页缓存；对照臂在**同一个对象**上把新助手函数 monkeypatch 成 no-op（只隔离这一函数的成本，不掺其他差异）；同时报绝对 µs/次与相对百分比，并单独测一个**病态形状**（生产里最大的那一档）。拿病态数字下结论前，先 `GROUP BY` 量一遍生产真实分布——病态档若比真实最大档还大两三倍，就不能把它的百分比写成停机理由。快路径设计：廉价字符预检跳过绝大多数负载。**替换/改写类机制要双端取样**：请求侧（内存对象）与持久侧（宿主/引擎库）分别查。两侧可能不一致。自己不写库不等于库里没有：内层引擎的摄取链可能把改写版存进库，原文只留在宿主转录库。
5. **提交与交卷三件**：功能一笔、文档/meta 一笔，直提交 main（主人偏好）。交卷 = 任务卡 Progress（每项带 commit 指针）+ 状态板翻终版 + 台账附记（修了哪些、明确没动哪些）。仓库的 pre-commit 钩子依赖本机没装的工具时，先用等价的 `uvx <tool> check <改动文件>` 跑一遍并把输出记进交卷记录，再 `LEFTHOOK=0 git commit`——不要在没跑检查的情况下提交，也不要把「钩子跑不起来」写成「lint 已通过」。

## 防御性实现约束（触碰线上行为/热路径的改动）

主人令「不要引入新的逻辑错误」时，落地为可验证清单，逐条自证：

- **共享 helper 的调用方意图相反时，行为必须由调用方表态**。给一条被多处共用的写入/插入/提交缝挂新行为前，先 grep 全部调用点，逐个问「它要的是同一个语义吗」。同一条缝可能同时服务「副本顶替旧行」与「副本追加到尾部」两种相反意图；无条件执行必然打挂一边，而那一侧通常只有既有测试能发现。形状：`helper(..., <flag>=False)` 默认关，只有真正需要的调用方显式开，并补一条「忘传 flag 的调用方不生效」的测试。
- **copy-on-change**：只复制要改的对象，绝不原地改输入（宿主可能复用输入对象）。
- **no-op 契约**：无变化返回原对象（或按宿主契约返回 None/原值）：不先改后说。
- **幂等**：拿第一次的输出再跑一遍，必须零动作。
- **范围先分层取证再收窄**：扫描/清扫类改动先按角色/来源分层定范围。全文计数里大半是引用噪声（工具输出里读代码/模板/文档产生的假匹配）。不分层 = 把提及当泄漏。先分层，再下口。扩面留指针，不即兴。
- **单一开关**：默认开、env 可关（`X=0`）、调用时读。
- **确定性**：同一输入永远同一输出（前缀稳定）。
- **模式/家族表先镜像兄弟实现**：grep 现有正则/清单照抄（跨工具一致、误伤面已知），不凭记忆自创。
- **改生产数据与服务写入并存时按 key 分批**：大表整表 UPDATE 会长期占住写锁、把在线服务卡住；按主键/会话分组，每组一个 `BEGIN IMMEDIATE` + `busy_timeout`，提交即放锁。跑前打含 WAL 的 `.backup` 快照并 `integrity_check`，跑前跑后各数一次命中数（前数进记录，后数必须归零）。需要停写窗口而服务不能停时，分批就是替代品，但要先量清单批耗时。
- **已改不等于已生效**：插件/网关类改动要重载进程才装载。自己无权重启时，把重启命令与重启后的核验写成**一条可执行脚本**交主人，别把「代码已提交」写成「缺陷已消失」。**这份脚本必须先对着旧进程跑一遍并看到它红**——用重启前的真实基数做阴性对照（例：缺模块告警 1202 行、无钩子支撑的 active 行 24 行）。交出去就全绿的核验脚本大概率是橡皮章。

## 红线

- **修完即停**：批次的终点是「全绿 + 可回滚 + 报告」，不是「顺手部署」。重启/生效时机由主人拍板。汇报里必须区分「已改」与「已生效」（插件改动在进程重启后的装载才生效）。
- 生产只读默认：不重启、不改 config/systemd、不碰数据库。一切验证走隔离沙箱。
- 两个高频返工点：①没见 RED 就写实现（TDD 退化成事后补测）。②沙箱探针没复刻生产启动链就下「加载失败」结论（实际是探针缺陷）。
