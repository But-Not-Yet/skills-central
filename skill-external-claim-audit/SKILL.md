# 技能库外部断言体检（防知识腐烂）

对象是一批 SKILL.md 里「写下来那一刻就开始过期」的断言：CLI 命令名与标志、仓库 URL、API 端点与参数、包名、版本号、方法名。流程判据与本机事实不在此类。

## 流程（按序）
1. **分诊**：脚本扫全库，按外部依赖信号（URL 数、CLI/包名词频、版本号）排序，圈高风险候选批。顺带从 state.db 拉 skill_view 加载台账：「从未加载」只证明没进回路，不证明写得烂——两个读法都要报。
2. **限额委派**：按批派本地子代理（delegate_task，禁云 API）。每个子任务的 context 里写死预算：每文件只核 2-3 条最高危断言、每条最多 2 次搜索，失败即标「无法核验」继续。不限额会让子代理在搜索循环里烧完 API 空手而归。
3. **亲验后才动手**：子代理的结论是自报，高置信也有假阳性。只修同时满足两条的：(a) 官方一手来源（官方 README/源码/release notes/活体 curl）直接命中；(b) 改错代价低。子代理说「不存在」而官方页原文就在用那个写法时，驳回不改。
4. **修法**：确证的改正文并留一行核验注（日期＋来源）；查不实的降级为「跑前 --help/实测对表」写法，不硬改；当时实测得来、网上查不到的变量（如训练环境 grep 所得），不删，加限定「换版本必须重新 grep，不许照抄」。
5. **收尾**：改动经 skill-library-sync 管线分发三库；rkllm 类主人点名封存的文件不碰。

## 一手来源验法（实测有效的具体招）
- GitHub 仓库迁移：`curl -sI <旧URL>` 看 301 的 Location 就是新组织名。
- PyPI 包名是否存在：直接 curl 包名页看标题；PyPI/debian 都会用 200 兜底页，**必须 grep 页面标题或内容**，状态码单独不作数。
- packages.debian.org：不存在的包也回 200（标题是「Debian -- Error」），要核 `<title>`。
- apt 仓库活性：探 `<版本>/dists/<代号>/Release`，不带版本号的裸路径 404 不代表整条路死了。
- arXiv API 用 https（http 会回空文件）；字段前缀以官方 user-manual 字段表为准，再用活体查询数 totalResults 佐证。
- CLI 标志是否存在：优先拉上游 README raw 文件 grep；源码 argparse 段（`_cli/run.py` 之类）比任何文档都硬。
- 同一工具在两个仓库体系里包名不同（NVIDIA 官方指南包名 ≠ Debian 仓库包名）：先确认技能走的是哪条安装路线，再拿对应体系的官方页核。

## 坑
- 子代理拿旧资料翻案新现状（拿发布博客核当前 CLI 清单）：核现状必须拉当前版文档或源码，发布类文章只当历史。
- 「网上搜不到」≠「不存在」：搜不到只降级为待核验，不许直接判虚构并删。
- 改完不跑同步脚本 = 改动只活在 default 一库，worker 照吃旧版。
