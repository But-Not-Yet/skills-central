# 无人值守任务规划（Overnight Mission）

## When to Use

用户要求「干到明早我来接力」式的无人值守长任务时。先把规划+问题清单交给用户批准，批准后才挂 worker——不要直接开工。

## /goal 常驻目标结构（用户批准任务序列后照此生成）

1. 任务序列逐条列出 + 任务源文件路径 + 「开工每轮先读任务卡 Progress 节，已完成的不重做」。
2. **终态分型条款（2026-10-04 主人裁定，取代旧「探索不开新实验」条款）**：/goal 生成时必须声明目标类型。终态行为按类型分派。
   - **科研/开放型**：完成判据满足后不停，自动进入探索循环。文献检索 → 方案规划 → 小规模受控论证/实验 → 收集结果 → 验证 → 下一轮。护栏：每轮开跑前预注册判据（新实验新判据，不动主线 FROZEN）。「小规模」要有显式资源上限（GPU 时长/样本数）。每轮必须产出落盘物（核验笔记/设计增量/结果报告）且过反思三行，无落盘物=该轮作废。结论与主线命题冲突时写入待拍板清单而不是自行改主线方向。升格为正式实验臂需主人拍板。
   - **工程/封闭型**：严格收口。完成判据全满足且交付物落盘后目标进入终态，后续 goal 推送只回一行「已完成。停止。」，不重跑核验。
   两类都必须把终态条款写进 /goal 正文——不写，系统不会自己有终态。
3. **唤醒分级**：只有绝对紧急（数据要丢、实验要断、方向二选一卡死且无默认动作）才唤醒用户。非紧急的「需要用户决定」问题先跳过、记下、继续干别的，汇总进晨间待拍板清单。
4. 截止时间写明（如「直到早上 10 点」）。
5. 开工 T0 先 `date` 实测时钟再排时间闸：目标文本里「今晚/明早 N 点」都相对**发令时刻**。规划会话与实际开工可能差几十分钟——按实测剩余时长重排全部时间闸再点火，否则全线踩闸。

## 拍板落定纪律

- 用户拍板后把决定写进任务卡的「拍板记录」节。连同用户给的**理由**一起记（理由会约束后续设计，比如否决某干预路线的理由决定了新设计不能踩同一个坑）。
- 用户把观察升格为正式实验臂时，负责想清楚**正结果和负结果各自对研究命题的作用**并预登记。两种结局都要有明确去处，负结果是划边界不是失败。
- 用户说「不理解/先跳过，回头再说」的项：冻结现有定性、明确标注不占工作量，不再追讨。

## 写任务卡即交付（用户说「写一个任务卡/goal prompt，我放到新会话去跑」时）
- 交付物 = 两个落盘文件：任务卡 .md + 对应 Goal_*.md（内含可整段粘贴的 /goal 正文）。照最近一张任务卡的结构（权限边界/任务序列表/纪律/防空转闸/Progress/反思/晨间汇总节）。写完立即停，不开始执行任务本身——即使用户说的是「今晚全量干完」。也要先把 /goal 正文全文贴进可见回复供过目，用户点头后才点火挂 worker。
- 用户口述的硬约束（指定机器、禁用工具、截止时间）原样写进卡顶「硬约束」节，并在 /goal 正文里重复一遍。执行体是新会话，只认文件。
- 用户列出任务清单后加一条「补充你认为必要的任务」授权。主动补上主实验的前置测量/前提检验类任务（如主实验成立条件需要先测的分布检验）。并在交付时点名说明补了哪些、为什么，请用户过目。
- 一晚跨两条研究线时给每条线设时间闸（如 03:30 切线、09:30 交晨间报告）。规则写「到点即切、当前小节写到哪停到哪、如实记录」——防止单线未完挤掉另一线。

## 架构

- **任务卡文件 = 唯一任务源**。在项目目录先写任务卡 .md（任务序列表：任务 | 性质 | 权限 | 依赖 + Progress 节 + 反思节 + 晨间汇总节）。执行体是全新会话，没有本会话记忆——目标、边界、格式、前情上下文全部写进卡里才作数。
- **长任务用后台 one-shot worker**（hermes chat -q fire-and-forget，或 tmux 起交互会话喂指令）。
- **cron 是看门狗不是劳动力**：Hermes cron 每次运行有 3 分钟硬中断（内置不变量），跑不了长任务。让它按小时巡检任务卡 progress 节，超时（如 2 小时）无更新就写 stuck 标记，早上用户一眼看到卡在哪。
- **delegate_task 不 durable**：父进程退出即丢，跨夜任务只走后台进程或 cron。

## 用户硬规则（写进每张任务卡）

1. 每完成一项 = 落盘 + 反思/自我批判节（证据、反例、下一步）。无反思节不算完成——这是防空转的核心闸。
2. 开工任何任务前先读任务卡 progress 节：已完成的不重做。同一文件无新证据重写两次 → 自我打断并写原因。排任务序列前先搜产物树的既有判据/结果文件（判据_*、*结果*.md、预注册类）。上一棒可能已把某项做完。已完成判决件的处置是核验产物存在与数字一致，不是重跑。
3. 权限边界写死在卡顶：哪些目录可写（默认只动项目目录树）。生产环境默认只读（每个例外单独列出并标注需批准）、不 kill 进程、不碰配置区。任务撞边界 → 标「待批」跳过，不越权执行。
4. 每个任务的产出格式与验收标准在卡上写明（引用文献逐字落盘、检索不到写「未找到」不许脑补——沿用 literature-verification 纪律）。
5. 晨间汇总：每项一行（做了什么/证据路径/自我批判一句话）+「待用户拍板」清单。
5a. 主人睡前令「进度落盘成日志/笔记类型散文，明早起来看」→ 项目根建**一份滚动日志**（散文体叙事，每事件一节带时间戳与实测快照，非条目流水），git 提交留时间戳。此后每交卷/验收/转折续写一节，绝不另起第二本——主人醒来只读这一个文件。日志末尾带代号白话对照表。「醒来要看的三件事」类决策清单放末节。
6. 汇报可读性（给用户的每份报告，含中途汇报）：开头五线头。①现在在哪②这次做了什么③结论是什么④对总目标意味着什么（总目标 = 卡顶写的纲领根件，不是上一张卡重述过的目标）⑤需要用户拍板什么。内部代号（假说号/阶段号/臂号）首次出现必须白话展开（维护一份代号对照表落盘，报告指向它）。缩写过的行话也算首现——把任务卡里的「自发发射」缩成「自发射」后仍要带括注。任务卡里出现过不等于读者记得（2026-10-04 主人纠正）。禁电报体：完整句子、有主语、术语首现即解释。报告分两层：上层白话给用户，下层技术细节给执行体自己。「如前所述」禁用——用户没有跨会话记忆，对齐责任在执行体。判决类汇报必须含「一句话版」：每条结论先给一句人话（可带一个具体例子），数字表作附件。用户回「没看懂」的报告即未完成传达。拍板项给 A/B 选项并各配一句适用条件，不堆裸数据。
7. 跨压缩生存纪律：任务卡只在任务开头被读一次，压缩后其内容只剩摘要。需要全程生效的规则除写卡外必须有落盘副本+进入组装层注入（见 lcm-summary-tuning 的压缩生存性节）。
6. 计划要激进不要保守：用户认为 agent 写代码快，反对为稳妥砍范围——任务序列排满。

## 外部材料进任务卡前的核验纪律

用户粘贴的外部 AI 对话/第三方分析进入任务卡前。其中每条事实性断言都要先对本地证据核一遍并在卡上标注核实来源。核过的和没核过的分开列，不许把别处的叙事直接当已核验结论写进方案。

- 关于本机仓库/二进制的断言（如「某功能不在树里、要重编译」）必须查三处才算数：git log --all（搜合并 commit）。在用二进制的 --help 直接输出、源码 arg 解析处。只看 grep 源码树容易漏掉已通过分支 commit 落地的功能。
- 「日志里零证据」类结论：先把日志目录整个 ls 一遍——stdout 日志可能被 logrotate 清空。真实证据在 .err.log / .gz 轮转文件里。
- 异机数字只当方向参考，本机复测后才进决策（对拍任务单列，不直接采纳）。

## /goal 系统适配（2026-10-04 夜班教训）

/goal 是无状态驱动器：每轮重推目标文本，执行体只有摘要记忆。它没有「目标达成→自动停止」机制，也没有内在的质量判断。所有终态和质量标准都必须由目标文本和任务卡显式写出，否则不会存在。

- **终态条款写进 /goal 正文（按目标类型分派）**：生成 /goal 时必须声明科研型还是工程型。终态行为照「终态分型条款」写死——科研型收口后自动进探索循环（带护栏）。工程型收口后一行终态声明。实测教训：无终态条款时收口后被推 17+ 次。而科研目标若按纯工程方式硬收口，会浪费夜间剩余算力——两种失败方向都要用条款堵住。
- **验收两层化**。任务卡每个任务的验收标准 = 存在性判据（文件/数字落盘）+ 健全性判据（一条可执行的具体检查：真样本端到端走通、分布外推理落在训练分数 ±3σ 带内等）。只写存在性判据时，六个完成判据可以全过而实验整体 FAIL——存在性验收是自证，不是检验。
- **冒烟的最小真实路径**：冒烟测试的通过标准 = 至少一条真实输入端到端走通主路径。合成流全过只是第一层，真实入口的 shape/类型/分布问题只有真样本能暴露。
- **远端长任务防会话终止**：后台 ssh 链会随本地会话终止被杀（实测两次，各损失分钟级）。Linux 端用 nohup 起、结果落盘后本地轮询文件。或前台跑带足 timeout + ServerAliveInterval。
- **Windows 远端（OpenSSH）防断连连坐（2026-10-04 实测，on-policy T4 跑通）**。ssh 会话里的直接命令与 PowerShell Start-Process 子进程都会被会话作业对象在断连时杀掉（实测：进程秒死、log 空文件）。必须 `schtasks /create /tn <名> /tr "<bat 绝对路径>" /sc once /st 23:59 /f && schtasks /run /tn <名>` 由任务计划服务拉起，与 SSH 会话解耦。三个坑：/tr 值上限 261 字符，参数长（如两个 sha256）写进 bat 中转。bat 要 CRLF 行尾。跑完 `schtasks /delete /tn <名> /f` 清理。监控走独立轮询循环数产物行数（容忍 SSH 瞬断，连续失败 N 次才报警），别依赖远端 stdout。
- **看门狗的盲区**：cron 看门狗只能发现「无进展」，发现不了「朝错误方向有进展」。反思节三行里必须含一行「当前结果是否与目标前提矛盾」——这是唯一能自测方向的通道。

## 仪器有效性闸门（INVALID ≠ FAIL，2026-10-04 主人纠正）

预注册冻结的是**判据**，不是**仪器**。二者必须分开，否则纪律会变成不重做的借口：

- **FAIL** = 仪器在工作分布上读数正常，假设不成立 → 落盘负结果，不重跑、不挪阈值。
- **INVALID** = 仪器在工作分布上读数本身不可信（分布外分数落在训练 ±3σ 带外、饱和、符号反号、传感器无响应）→ 这是工程故障，**不构成对假设的任何判决**，禁止写成负结果。
- 设计文档必须预注册仪器有效性检查（一条可执行的读数健全性检验）与其失败分支。「INVALID → 修仪器 → 同判据重跑」。**修仪器 + 原判据重跑属于原授权范围内，不是 p-hacking，不需要重新拍板**。只有改判据/改假设才需要拍板。
- 自查句式：报告里写「判决=FAIL」之前，先答一句「仪器在工作分布上读数可信吗，证据是什么」。答不出就是 INVALID，不是 FAIL。
- 典型误用（实测犯过）：探针在生成分布上 softmax 饱和、分数反号，仍按冻结判据判 FAIL 并停止。把「测不了」当成了「测出来是负的」。正确动作是当场修观测（on-policy 标定）后同判据重跑。
- **A/B 对照的累计 token 读数被轮数支配**：每轮请求重发固定前缀（数万 token），累计 input_tokens ≈ 轮数 × 前缀 + 每轮增量。两臂 API 轮数不同（模型策略差异）时，token 差反映的是策略不是干预。设计时预注册自动不可比条款：双臂轮数差 >20% 则 token 数字判不可比。只报行为指标（成功率/换招率/放弃率——行为指标不受轮数支配）。要拿 token 当主指标，先修任务脚本强制双臂同调用序列。同一仪器坑连撞多次才结案 = 缺这条预注册。

## 会话阵亡后的进度重建与交接（跨模型接力）

会话死掉（空回复循环、平台截流）后把任务交给另一模型续跑时照此重建——只认原文与盘面。不认会话叙事。

0. 先回死亡前的最后一条**用户指令**：其中未兑现的交付物定义续跑的第一产出——那不是「下一步实验」。是欠用户的账，重建完成前最先补交付。
1. 用 session_search 滚动读死会话的原消息，重建时间线（时间戳逐条抄）。压缩摘要只是检索线索，数字与状态回原文读出后再用。
2. 逐项核验声称的产物：本机文件 sha256 + mtime 对账（冻结判据类文件必须复算哈希）。远端产物直接 ls 目标目录。死亡点附近报错或未启动的工具调用（含批准环节失败导致 command was not started 的）一律按没执行处理。「已传/已跑」的叙事不作数，目标机文件系统说了算。
3. 代码层面的「已核验/已比对」断言用程序复核（importlib 加载比对 pattern 或函数源），复核结果写进交接卡。
4. 交接卡落盘在任务产物目录，固定节。死亡时间线 / 已完成（证据+哈希）/ 可直接复用的数据 / 下一步（命令可整段粘贴）/ 代码缺陷清单 / 环境与硬约束 / 纪律原文（可整段粘贴重述）/ 范围外挂账。给下一棒的每条命令都要能直接粘贴跑。上一批挂着的待办单独列「范围外」，不塞进新任务序列。卡内引用的每条路径在交付前用脚本程序化解析核验（相对路径对多个基目录逐一试解析）。缺失清零再交付——手写路径错一条，下一棒第一次按图索骥就落空。
5. 汇报走五线头，明示「准备好了」，交接卡路径写进汇报。

## 纲领对账与命名空间（多夜任务卡链）

多夜任务卡链有个结构性漂移源：每张卡传的都是上一棒重述过的目标，传几代之后。链上没有任何人手里还握着纲领原文。对账纪律：

- **卡顶写纲领根件**。每张任务卡/交接卡顶部写明纲领根文件路径（原始构想/背景调研文档——研究纲领的原文，不是任务卡）。包报告五线头④的总目标 = 根文件里的纲领。对卡链上重述过的目标打分是自我记账，不是对账。
- **改纲必须显式落盘**：收窄/改道/换对象是合法决策，但要落盘记录（谁定的、哪些象限挂起、何时复核）。盘上没有改纲记录的收窄 = 基准漂移，回顾时按事故处理。
- **回顾先读根件**：「目标达成了吗」类汇报第一步是重读纲领根文件再逐条对表。把「静默收窄」本身当一等发现上报——基准漂了，分数再高也只是在为收窄后的目标记账。
- **包命名先查全项目命名空间，含设计文档里已规划未实现的组件**：设计文档占的名视同已占。新包与既有设计子系统撞名，会把「设计存在」误读成「已实现」，把缺口藏进名字里。
- **「已实现/未实现」的口对着设计文档的独特标识符下**：grep 设计里特有的术语/参数名/机制名。只在设计文档出现的 = 未实现。「存在功能相似的别的东西」不构成实现证据。
- **「计划下一步」的落盘形态 = 可点火件**：下一步计划要落到预注册草案（判据 + 阵亡条款写死）。用户一句 Goal 即触发 T0 冻结开跑。纯散文计划不构成交付。

## 陷阱

- 昨晚提前收工多半是任务清单排少了或没有防空转闸——排任务时按整晚量排。每项都要能独立产出落盘物。
- 收尾空转：任务全部收口后若 goal 推送仍反复到达，一律回一行「已完成。停止。」即可——不重跑核验、不展开细节。已实测核验过的完成状态不因重复推送而重新检查。
- 需要碰生产/训练硬件的任务单独列「需批准」级，与目录树内的零风险任务分开排依赖。
- 长会话压缩污染死法（2026-10-04 夜实测：369 条会话死在交付前一步）。上下文压缩把工具结果剥成占位（Duplicate tool output / SKILL_PRUNED）。加上每轮纪律复述文本膨胀 → 执行体循环重读同一文件。把压缩残留当事实（幻觉出盘上不存在的文件并追讨）。症状出现＝收口信号：立即换新会话接力，按「会话阵亡后的进度重建」流程走。产物层在盘上无损，丢的只是会话叙事。
- 复读截流是另一种长会话死法：运行时检测到生成陷入复读循环会直接掐流并丢弃残段回复。磁盘产物无损，只是那段话没说出来。恢复 = 换模型（/model）或原样重发。向用户解释时先说清「丢的是输出不是数据」。数字密集型超长会话（连续几小时报数）是高危场景，收口宜早不宜迟。
- 续写多轮产物集前先找规范账本：同一套轮次文件若已在某目录成套存在（按 mtime/命名序列可辨）。续写必须写进那套。另起一份平行副本会造成双账本分叉，收尾时还得人工裁决哪份作数。先 ls 既有目录再落笔。
- 同一错误第二次出现时，第二次修复必须换层级。从改语句升级到改结构（惰性初始化→预热预分配、单点修补→全家族路径 grep）。重启前把该错误家族的残余代码路径全部排除再点火。盲试第三次烧掉的是整段 GPU 窗口与看门狗周期，而同族 bug 还会在下一个调用点等着。
- 中断恢复先验盘后重做：回合被中断（进程停止/会话截断）后。先逐项核对目标文件里计划内改动是否已落盘（grep 每个编辑的锚点串），只补缺失项。盲目重放会覆盖已完成的编辑，并把已完成的工作误报成失败。盘面是唯一事实源（「会话阵亡后的进度重建」同一原则，收窄到回合级中断）。
- 看门狗轮询只探「结果文件存在 + 行数爬升」会白等：进程首行崩溃后结果文件永不出现。轮询静默跑满整个周期（实测白等 55 分钟才发现）。轮询体必须同时 grep 日志尾的错误关键字（Traceback/RuntimeError/AttributeError），命中即收口报警。长 GPU 任务的看门狗从第一次轮询就带错误探测，不等首轮失败后再补。
- **进程出现型哨兵的三连自中坑（2026-10-07 实测连犯两次）**。`pgrep -f '某路径'` 的模式字符串写在哨兵自身 cmdline 里，必然自中。第一次中了常驻服务（被盯的引擎就住在 `build-hip/strata --serve` 路径下）。第二次中了脚本文本（模式词就写在脚本里）。规则：① 用 `pgrep -x` 按**进程名精确匹配**（comm 级，bash/常驻服务永不自中）。② 哨兵脚本**落盘成文件再跑**，cmdline 只含文件路径不含模式词。③ 被盯路径若同时是常驻服务路径，必须排除其特征参数（如 `--serve`）。触发即退出 + notify_on_complete 报警，副信号（如 ctest）走心跳不报警。
- **共存内存账（哨兵约束下的停服决策）**：判定「要不要停服窗口」前先量「执行体常驻时的 MemAvailable」对「任务峰值」。装得下就不停，不停则 CPU 核争用会让 ETA 估计偏乐观（ETA 按争用后计时重标定）。执行体配置一变（主人换模型/换 pack），内存账必须重新实测。旧 RSS 快照不作数（2026-10-09 实例：Strata MoE RSS 49.9GB → 换 llama-server GPU 常驻 RSS 6GB，MemAvailable 6.2 → 52.1GB，停服窗口整本账作废）。
- **点火动作必须回读闭环**：「挂上」看门狗/编排器后，结束回合前必须验证日志文件存在且首行已写入。以「这就点火」一句话收尾而工具调用根本没发出。是链条静默断裂的头号死法（机器空转一整晚没人发现）。归因中断前先 grep agent.log 的 `Interrupt requested`：无中断记录 + `finish_reason=stop` = 回合自然结束、承诺未执行——别把锅甩给「主人插话」。主人可能早在睡。
- **无人值守链用 /goal 驱动，不用主会话的「我稍后做」**：goal_judge 每轮对照 verify 判 DONE/CONTINUE，空承诺混不过收工。契约至少写 outcome/verify/stop_when 三字段（写法见 hermes-goal-authoring），stop_when 必含「恢复服务态」出口。链死在任何一步都要把停掉的生产拉回来。
- **本机长跑后台进程双保险**：不带 persist_on_release 的本机后台任务随会话回收被杀，跑一半结果悬空（通知永远不来，直到主人问「是不是中断了」才发现）。点火必须带持久化，且脚本自带逐单元增量落盘 + done-key 跳过续跑——重跑即幂等，断了续上不重烧。点火后别干等完成通知：设一个早期检查窗，确认**首条结果真的落盘**再宣称「在跑」——进程活着 ≠ 端点活着 ≠ 数据在落，只有落盘文件带计时与逐单元字段才算进度实锤（对照实验还要每单元记录耗时，速度评审才不用重跑）。
