# 灵感笔记背景调研 / Previous-Work 筛查

面向 CS/ML/系统/社科文献的 web_search 调研流程。数学定义/定理/证明类问题走 research-kb-usage skill（research_kb 语料库），两者不混用。Venue 速查与 GitHub 可行性启发见 references/venue-map.md。用户要求落盘时的逐篇文献文件 / README 索引 / 路线矩阵 / 实验设计骨架模板见 references/deliverable-templates.md。模型离线取证配方（GGUF 头解析、safetensors 嵌入读取、字面量可拼性 DP）见 references/offline-model-forensics.md。生产 llama-server 行为探针的已验证模式（logit_bias 阶梯、seed 扫描、finish 歧义、收尾 margin）见 references/llama-server-probe-patterns.md。行为实验动手前先做文件层取证定靶。会话层吞消息的诊断（state.db 取证、执行模型溯源、跨模型免疫探针）见 references/session-truncation-forensics.md。聊天模板 overlay 注入（常驻纪律放 system 尾的位置学、条款文本设计、沙盒渲染验证、--chat-template-file 部署回滚）见 references/chat-template-overlay.md。

## 铁律（always-on）

1. **只读**。绝不修改、移动、重命名用户的笔记。全部交付物直接写进对话，不落盘报告文件，除非用户明确要求。
2. **逐条验证笔记引用的每一条文献**：存在性、venue/年份、关键数字（性能倍数、百分比、会议届次）。用验证表呈现，发现不符要指出。高估和低估都会出现（地位被写低如 Best Paper 未标注、竞争者被漏写都常见）。
3. **「无人做过」的声明必须做排空检索**：对笔记声称的空白组合做 2-3 次针对性搜索再下结论。结论分三档：字面成立（无人做）/ 缝隙被挤占（列出竞争者+把声明收窄到具体机制）/ 已被占据（如实告知）。相邻地带拥挤度按年份列出并给出窗口期估计。
4. **不凭记忆断言论文 venue/年份/数字**——全部检索核实后再写进报告。
5. **外部 AI 对话摘要里引用的文献同样逐条走铁律 2 核验后才可入报告**——对方是 AI。引用可能真但流程不能跳。核验结果标注级别（检索级/源码级），未升级源码级的标「检索级」。
6. **对比+补充新观点时每条新观点带日期标注**，方便用户增量合并进笔记体系。对照用户原始笔记的结构组织输出（核心要点→对比→新增观点）。

## 流程

1. **全量读取**：search_files 用 `*灵感*.md` 等模式找齐笔记（也检查速记/散记文件），read_file 逐篇读完，确认篇数后再开工。
2. **第一轮·核心验证**：对笔记自引文献批量 web_search，每轮 4-5 个并行调用。查询用「独特多词短语 + venue/会议名」提高命中。短词（如单个术语、常见单词）会命中大量无关页面——遇到噪声换更长区分性查询重搜。不采信存疑的 top 命中。
3. **第二轮·竞争扫描**：搜笔记**没提到**的邻近/竞争工作，重点最近 12 个月。特别警惕「框架愿景型」论文（如 memory OS、agent 基建类）对「组合创新型」想法构成的定义权威胁。
4. **第三轮·排空 + 理论支柱**：对核心创新 claim 做组合排空检索。社科类补齐理论经典锚点（该领域必引文献）。
5. **热点领域的月份加权终扫**：KV cache/agent/记忆管理这类月更赛道。报告定稿前用 arXiv 编号模式（如 `arxiv 2609`）+ 「September 2026」式时间词再做 4-5 次终扫。竞争者的「首个」声明可能在几周内出现，缝隙声明的有效期以「检索日」计。竞争对手论文要 web_extract 读全摘要。搜索摘要会误导（看似直接竞争、实为可复用的评测基建，如 benchmark/榜单类论文）。
6. **疑难论文**：用 web_extract 读 arXiv abs 页，比对摘要与笔记 claim 是否一致（arXiv export API 不稳时的替代通道。arXiv 检索细节见 research:arxiv skill）。abs 页同时核对题名/版本/日期：搜索结果可能显示 v1 旧题名。v2 改名/大改本身是竞争者活跃迭代的信号——报告按 abs 页现题名为准并注明曾用名。
7. **深搜落盘批次**（用户要求「所有结果落盘/方便后续审阅」时启用，模板见 references/deliverable-templates.md）。① 每个项目建独立文件夹 + `literature_review/` 子目录。② 深搜每轮 2-4 个并行 web_search × 2-3 轮汇成候选池。③ 分批 web_extract 抽 abs 摘要（每次 ≤5 URL，char_limit 4000）。④ 用 execute_code 以数据驱动的 papers 列表一次生成全部逐篇文件 + README 索引（比逐文件 write_file 快一个量级）。⑤ 提升方向分析 + 初步实验设计单独成文放项目根目录。
8. **撰写汇报**：按下方格式，结尾给横向优先级排序（价值×可行性×窗口期）。

## 汇报格式（用户指定的固定维度，每篇笔记都要含）

- 背景调研汇报：文献验证表 + 未提及的竞争者 + 缝隙判定
- 创新点分析：成立点与需收窄点分开写
- 论文可能性：给出具体 venue，按独立研究者身份评估可及性
- GitHub 项目可能性
- 学术贡献 / 业界贡献与意义
- 推进方向难度×价值表：每行「难度 | 价值 | 建议+启动成本」
- 汇报开头 BLUF（方法说明 + 总核验结论），结尾横向对比总表 + 优先级建议。用「立即做 / 先做试金石 / 并行积累」标注。

## 陷阱

- 单一查询不足以下核实结论：search 命中 + arXiv abs 页 extract 双源确认才算验证过。
- 「A Research Agenda」类研究议程论文是双刃剑：既是选题合法性的最佳论据（缺口被点名）。也是竞争预警（议程会吸引别人来做）——报告里两面都要写。
- 组合创新类想法的窗口期短：组件全存在时，竞争在定义权而非发明权。给用户的建议必须含两条退路。低成本先行实验（验证最便宜的那条命题）+ 开源工具链保底（论文不成仓库仍有用户价值）。
- 竞争者插旗相邻声明时（如「首个 agentic KV 管理」）不要整体放弃。逐个枚举原缝隙声明的限定词（无损/注入式/版本化/统一表示…）。把 claim 重写到「仍然成立的限定词组合」上——缝隙收窄不等于消失。
- 工程侧缺口评估必须查实践者渠道（GitHub discussions/issues、厂商博客、官方文档、man page）。论文检索查不到「上游已经原生实现了什么」。例：llama.cpp 2026 已有 context checkpoints/host cache/KV shifting，原型应构建其上而非从零造轮子。
- 长报告（>8K 字）直接发对话会被截断（实测同一次汇报截断三次）。用户要求落盘时写 .md（按用户偏好新建独立文件夹组织），对话里只给压缩版结论。用户决定放弃某条调研线时，把已获发现归档进报告附录，重启时不必重查。
- execute_code 批量生成落盘文件时，列表的每个字符串元素必须同时有 ASCII 开引号和闭引号：以全角引号「起头的行若漏写开引号，整个脚本 SyntaxError、一个文件都不会生成（CJK 文本高频踩坑，发脚本前扫一遍行首）。
- 实验设计遵循「科学问题与规模问题分离」。模型无关的假设先在可用的标准小模型上验证（零生产风险）。把换模型/动生产的路线拆出关键路径、冻结到新硬件到货。每个实验阶段写明成功门槛（具体数字/统计标准）与不成立时的退路（benchmark 短文、负结果附录）。
- 可行性结论用路线矩阵呈现（每行：路线 | 资源代价 | 生产风险 | 裁决）。资源代价引实测数字（RAM/VRAM 余量、权重体积、prefill 实测耗时），不写形容词。
- 控制标记（ChatML 族）研究先给**死亡分型**定任务设计，再按**词表免疫**选执行模型。标记在 Qwen 系词表里是单 token 且兼任 eos：思考在**概念层面**处理它就可能直接预测出该 token。服务端按 EOS 截流、skip_special_tokens 把它从文本剔除，整条消息变空。**A 类·直接诱导**（任务本身要求输出/复述该 token 的原始形态）= 确定性死亡：负向 bias（-20 也压不住）。强化思考纪律、消毒 rc 重试全部实测无效——只有规避，任务设计层永不要求原始形态。需要原始形态的实验一律走 API 脚本（chr() 构造 + JSONL 落盘，被试的死是实验数据不是会话事故）。**B 类·间接诱发**（讨论相关概念时连带预测到它）= 概率性死亡：靠上下文密度控制 + 死亡后续写恢复（人工续写实证 4/4。消毒重试在直接诱导场景 0/6——两类不可互推）。模型验证配方、判据与否决清单见 references/session-truncation-forensics.md。占位符纪律（__IM_END__／描述式写法／代码 chr() 构造字面量）依旧全通道遵守：让模型自己永不排放该 token。对异家族模型也是输出卫生。注入模板的条款自身也不得含原始形态或名称——条款每轮随请求发送，不能让它自己成为诱发源。
- **常驻指令的位置学：文本越靠后权威越强**（recency。Lost in the Middle 实证）——标准纪律要放整个 system 块的收尾。SOUL/memory 在 system 头部＝最弱位，别当强约束用。本部署 system 收尾是模板内建 terse 提示，纪律注入走聊天模板 overlay（拼在 terse 之后＋kwarg 开关默认开）。改行为前先提取模板读它的内建提示词（terse 风格层、工具 MUST 条款、preserve_thinking 历史回灌）。它们可能已在压你的预期。规程见 references/chat-template-overlay.md。
- 归因先取权威执行记录：断言「哪个模型/组件导致了某行为」前。先读日志里的实际调用行（Hermes 栈：agent.log 的 `API call #N: model=...`）——会话系统提示与模型切换通知只反映配置意图。不反映实际执行。按通知重建时间线会得出错误因果（把「主动切回旧模型」误判成「新模型也被截断/切换失效」）。用户对归因错误直接纠正，改完要回写已落盘报告。
- 同一文件多处 patch 必须串行发（同回合并行发同文件 patch 会竞态丢改。不同文件可并行）。跨文件补账先 read_file 定位原文再写 old_string。相邻文件的表述会记串（对照表在汇总文件、正文在结果文件时尤其如此）。
