# 多子目标任务书模板（Goal + Subgoal）

当任务不是「一句话判据」，而是「一次系统排查 / 一次多阶段改造」时，任务书用这个结构。
用途：把一份长任务书当附件贴给新会话，goal prompt 只指向它。

## 为什么不用平铺清单
平铺的 A1–A5 / B1–B5 清单有三个毛病：
1. 不能独立分派——看不出哪几条能并行给不同子代理。
2. 没有依赖关系——不知道哪一条必须先做。
3. 证据要求散落在正文里——执行者容易漏。

Goal + Subgoal 结构把这三件事变成结构字段，执行者不用猜。

## 模板

```markdown
# <任务名>任务书

> 版本 / 目标仓库 / 当前状态

## Goal
<一句话判据。必须能回答「做完没做完」。>

**一句话判据**：<能明确回答的问题；答不出来 = 任务未完成>

## 0. 背景事实（已核实，勿重复发现）
### 0.1 仓库/环境状态
### 0.2 关键接口/钩子/入口
### 0.3 已确认的症状
### 0.4 已知历史缺陷（已修或部分修，勿当新发现）
### 0.5 已排除项（附证据，避免新会话重跑）

## Subgoals

### SG1 · <名称>（无依赖，先做）
**目标**：
**做法**：1. 2. 3.
**证据锚点**：
**产出**：

### SG2 · <名称>（依赖 SG1，可与 SG3 并行）
...

### SGN · 修复方案与验收（依赖前面全部）
**目标**：给出分优先级修复方案，不直接改文件。
**做法**：按「是否影响用户可见」排序；每条给改动文件:行号、风险、回归测试计划、回滚方式；标注责任方（本仓 / 宿主 / 外部依赖），不越界修别人的锅。

## 方法与约束
- 允许子代理并行：建议 N 路，先做完 SG1 再分派。
- 每条结论必须带证据：文件:行号 / 测试名 / 日志时间戳 / SQL 结果。无证据的推断标「假设」。
- 审计阶段不改文件；修复方案单独列。
- 不碰 <禁止改动的仓库列表>。

## 必载技能
<按任务列出>

## 可靠信息来源（按优先级）
1. 源码本体（唯一事实源）
2. 测试套件
3. <宿主/上游源码>
4. <历史记录库>
5. 运行时日志

## 交付物
1. 报告结构（分节列出）
2. 最小可复现测试（若发现缺陷）
3. 测试基线结果

## 验收标准
- [ ] 每个判定都有可核验的证据锚点
- [ ] <逐条列出必须明确回答的问题>
- [ ] 明确区分责任方
```

## 写作要点

1. **Goal 只写一句话判据**。判据要能被第三方核验，不写「做好排查」这种无法判定的表述。
2. **每个 SG 必须能独立执行**。给一个子代理一个 SG，它不需要读别的 SG 就能开工（依赖关系写在标题里，不是正文里）。
3. **证据锚点是硬要求**。每个 SG 单独列「证据锚点」，不写在做法里——写在做法里会被跳过。
4. **0.5 已排除项是最省时间的一节**。把上一轮已经查实并排除的方向写进去，新会话就不会重跑。
5. **不要在任务书里写「可能」「大概」**。判据要么可核验，要么标成「假设」。
6. **责任方必须区分**。同一个症状可能由本仓、宿主、外部依赖三方之一造成；不分责任方，修复方案会越界。

## 与 goal prompt 的配合

任务书写进永久路径（如 `~/.hermes/cache/` 或 `~/Documents/`），goal prompt 第一行指向它：

```
/goal 按 <任务书绝对路径> 执行 <任务名>（该文档为唯一任务书，含全部子目标与证据要求）。
done when: <从任务书验收标准里挑最硬的几条>
verify: <怎么核验报告>
constraints: <红线>
boundaries: <允许读写范围>
stop when blocked: <拿不到关键证据时的止损条件>
```

契约块会被 judge 截断到 2500 字符，所以 done when / verify 只写最硬的判据，详细内容留在任务书里。
